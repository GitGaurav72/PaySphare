7. IMPORTANT DESIGN PRINCIPLES
============================================================

Follow these rules throughout the implementation.

1. Do not expose entities directly from controllers.

Use DTOs.

2. Do not put business logic inside controllers.

Controller:
    request handling
    validation trigger
    response mapping

Service:
    business logic

    persistence

3. Use constructor injection.

Avoid field injection.

4. Use appropriate transaction boundaries.

@Transactional

for write operations where required.

5. Use:

@Transactional(readOnly = true)

6. Use BigDecimal for salary.

7. Use LocalDate for salary effective dates.

9. Use EnumType.STRING for enums.

10. Avoid N+1 queries.

11. Use pagination for employee listing.

12. Never load all 10,000 employees just to display a table.

13. Validate incoming request DTOs using Jakarta Bean Validation.

14. Implement centralized exception handling using:

@RestControllerAdvice

============================================================
18. SALARY UPDATE BUSINESS LOGIC
============================================================

This is important.

When a new salary becomes effective:

Current salary:

effective_from = 2026-01-01
effective_to   = NULL

New salary:

effective_from = 2026-08-01
effective_to   = NULL


The old salary must become:

effective_to = 2026-07-31


Then insert the new salary record.

Do this atomically inside one transaction.

Example:

@Transactional
public SalaryResponse createSalaryChange(...) {
    ...
}


Never allow two current salary records for the same employee.

Do not allow overlapping salary periods for the same employee.

Do not silently overwrite salary history.

============================================================
28. CONCURRENCY / SALARY UPDATE
============================================================

Pay attention to concurrent salary updates.

Potential problem:

Two HR managers simultaneously create a salary update.

Both requests might see:

effective_to IS NULL

and both create a new current salary.

Design the implementation to avoid this.

Consider:

- transaction isolation
- pessimistic locking where appropriate
- optimistic locking/versioning
- database constraints where practical

Choose the simplest reliable solution.

Explain the decision in documentation.
